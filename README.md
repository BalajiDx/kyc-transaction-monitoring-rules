# KYC & Transaction Monitoring Rules

A learning project on anti-money-laundering (AML) monitoring: KYC data-quality checks and six transaction-monitoring
rules written in **SQL** and in a **Python rules engine**, alert scoring and prioritisation, sample **investigation reports**
and a monitoring dashboard.

> **Synthetic learning project.** All customers and transactions were generated by `01. Dataset/generate_dataset.py`
> (seed 11). No real customer or bank data is used. Thresholds, review cycles and country codes are **illustrative**
> and are not compliance or legal advice. A real programme follows the bank's risk assessment and the regulator's rules
> (in India, RBI's KYC Master Direction and the PMLA).

## How it works
1. **Generate** a year of activity for 1,800 customers (194,492 transactions). The generator plants 51 suspicious cases across five
   typologies, and it also adds **legitimate look-alikes** (shops paid by many UPI customers, property-sale proceeds, cash
   businesses) so the rules face realistic false positives. Some planted cases are deliberately evasive.
2. **KYC checks** (SQL K01-K03): missing documents, overdue periodic reviews, high-risk customers without enhanced due diligence.
3. **Monitoring rules** (SQL R01-R06 and `rules_engine.py`): structuring, pass-through, income mismatch, funnel accounts,
   high-risk jurisdictions and sudden spikes.
4. **Alerting:** rule hits are consolidated into one alert per customer, scored (rule weights x customer risk, + PEP) and given a priority.
5. **Evaluation:** the engine compares alerts with the planted cases, which the rules never see, to report recall and precision per rule.
6. **Investigation:** four case files, three escalations and one closed false positive, written the way an analyst would.

## Results
| | |
|---|---|
| Rule hits / customer alerts | 191 / 98 (5.4% of customers) |
| Planted cases caught | **48 of 51 (94%)** |
| Alerts that are true cases | 49% (the rest are legitimate look-alikes) |
| KYC reviews overdue | 176 customers, including 67 of 102 High-risk customers |
| High risk without EDD | 24 customers (4 PEPs) |

| Rule | Description | Customers flagged | Recall | Precision |
|---|---|---|---|---|
| R01 | Cash deposits just under ₹50,000 | 23 | 79% | 48% |
| R02 | Large credit moved out within 2 days | 28 | 100% | 43% |
| R03 | Credits above 3x declared income | 43 | 100% | 63% |
| R04 | 15+ different senders in 7 days | 30 | 100% | 27% |
| R05 | Transfer with high-risk jurisdiction | 7 | 100% | 100% |
| R06 | Monthly credits above 5x own normal | 53 | n/a | 68% |

What the numbers say: R01 misses structuring that is spread over more than 10 days; R04 is noisy because shops look like
funnel accounts; alerts where several rules fire together are much more likely to be real. The tuning options are in
[`Rule Catalog.md`](Rule%20Catalog.md).

## How to run
```bash
cd "01. Dataset" && python generate_dataset.py && cd ..          # optional: data is included
cd "03. Python Rules Engine" && python rules_engine.py && cd ..   # rule hits, alerts, evaluation
sqlite3 kyc_tm.db < "02. SQL Rules/00_Create_Tables_And_Load.sql"
sqlite3 -header -column kyc_tm.db < "02. SQL Rules/R01_Structuring_Cash_Below_Threshold.sql"
```
Python 3 with `pandas` and `numpy`; SQLite 3.25+. The SQL and Python versions of each rule flag the same customers.

## Dashboard
`05. Dashboard/Dashboard Images/` shows two report pages. **They are rendered from the rules output with Python as layout
mock-ups, not screenshots from Power BI Desktop.** `DAX/Measures.dax` has the measures to build the real report on
`Alerts.csv`, `Rule_Hits.csv` and `Customers.csv`.

## Skills shown
KYC and AML concepts (typologies, risk-based review cycles, EDD, PEP, STR escalation), SQL window and self-join logic,
Python rule engines, alert scoring, measuring rules against known outcomes, investigation write-ups.
